\begin{abstract}
Software testing is an important part of software development because it helps check that a system works as expected. However, writing test cases manually can take a lot of time, especially when there are many requirements to test. This thesis investigates how AI can be used to generate system-level test cases from requirements and related system information. The main problem is to study whether AI-generated test cases can cover the same requirements as manually created test cases, and if AI can do this with fewer test cases. To investigate this problem, an AI-based pipeline was created using LangChain and Azure OpenAI Service. The pipeline generated test cases in a structured format, including test case ID, requirement IDs, description, steps, and expected result. The pipeline also included traceability generation, where the generated test cases were linked to requirement IDs. The AI-generated test cases were then compared with manually created test cases from Volvo Construction Equipment. The comparison focused on requirement coverage, number of test cases, requirement links, repeated links, test-case matching and a support step-level evaluation. The results show that the AI-generated test cases covered all 22 shared requirements, which was the same requirement coverage as the manual test cases. The AI-generated test suite also used fewer test cases, 7 compared to 9, and had 0 repeated requirement links. The step-level evaluation showed that the AI-generated test cases often followed the same main test idea as the manual test cases, but they were usually less detailed. This shows that AI can support test case generation from requirements, but the generated test cases still need to be reviewed before they can be used for testing a system.
\newline

\textbf{Keywords: AI agent, Large Language Model, Test Case Generation, Requirements-Based Testing, System-Level Testing}
\end{abstract}

\section{Introduction}
\label{intro}
Software development includes many activities that help make sure that a system is reliable and works as intended. One of these activities is software testing, which is used to check system behavior and find problems before release. 

Software systems are becoming larger and more complex, which also makes testing more difficult. Testing is challenging because it must check that the system behaves correctly in different situations, while larger systems often contain more functions, dependencies, and possible errors \cite{whittaker2002software, sommerville2016software}.

At the same time, artificial intelligence (AI) has developed quickly and is now being used in software engineering. Large language models (LLMs) are especially relevant because they can understand and generate natural language and code \cite{zhang2026survey}. This makes them useful in software testing, especially for tasks where requirements and test cases are written in text \cite{wang2024software}. Previous studies have also examined how LLMs can generate test cases from natural language requirements \cite{korraprolu2025test, bhatia2024system}. 

Zhang et al. \cite{zhang2026survey} show that LLMs are being studied in many different software engineering tasks. Software testing is one of the areas where these models are also starting to gain more interest \cite{wang2024software}.

This degree project is carried out in collaboration with Volvo Construction Equipment and investigates whether an existing LLM can be used to generate system test cases from requirements. The project focuses on one specific use of AI in software testing and studies how this can be explored in a real industrial setting. The aim is not to address all challenges in software testing, but to examine one specific case where LLMs may be useful.
\subsection{Background}
System test cases are commonly created from a test basis, which includes documentation from which system requirements can be identified, such as requirements and other system documents \cite{istqbTestBasis}. In practice, creating these test cases often involves manual test design by test engineers, which can become time-consuming when the system is large, complex, or contains many requirements and interfaces \cite{mustafa2021automated}. Earlier research shows that automated test case generation from requirements is already an established area. Mustafa et al. \cite{mustafa2021automated} show that many earlier methods are based on structured models such as Unified Modeling Language (UML) diagrams, activity diagrams, and use cases, rather than the less structured requirements that are often used in industry.

In recent years, AI has developed quickly, and LLMs have shown potential in several software engineering tasks. In software testing, recent research shows that these models are already being explored for tasks such as test case generation and test design \cite{wang2024software}. This makes them relevant to study in situations where requirements are written in natural language instead of more formal models.

The specific focus of this project is to examine whether an existing LLM can be used to automatically generate system test cases from requirements. This is relevant because test case creation is often a manual and time-consuming task in industry. Recent research has also started to study this problem more directly. For example, Korraprolu et al. \cite{korraprolu2025test} compare different LLMs for generating test cases from technical requirements written in natural language.

The project is therefore relevant from both a practical and a research perspective. In practice, there is a need to reduce manual work and make test case creation more efficient. From a research perspective, it is still important to understand how well LLMs can support test case generation from real industrial requirements.


\subsection{Related work}

Previous research shows that automated test case generation from requirements is an established research area. Mustafa et al. \cite{mustafa2021automated} show that many earlier studies focused on generating test cases from structured requirement models such as UML diagrams, activity diagrams, and use cases. This indicates that much previous work has relied on more formalized inputs than those often available in industrial practice.

More recent research shows that AI is becoming increasingly relevant in software testing. Wang et al. \cite{wang2024software} explain that large language models are now being used in several testing-related tasks, including test case generation and test design. This suggests that AI-based methods may offer new ways of handling less structured requirement inputs.

In addition, recent work has started to examine test case generation directly from natural language requirements. For example, a 2025 comparison study evaluated six large language models for generating test cases from technical requirements written in natural language, showing that this problem is now being studied more directly in an LLM context \cite{korraprolu2025test}.

Together, these studies show that automated test case generation is an established research area, while recent AI-based approaches open up new possibilities for practical requirement-based test generation. This supports the relevance of investigating how AI can be used to generate test cases from industrial requirements and that there is a gap between this investigation and previous work.

Compared to previous studies, this thesis focuses more on a practical industrial case. Some earlier studies used structured models, such as UML diagrams, activity diagrams and use cases, while this thesis uses requirements and related system information from Volvo Construction Equipment. This thesis also compares the AI-generated test cases with manually created test cases from the company. Therefore, the focus of this thesis is to evaluate how an AI-based pipeline can support test case generation in a real industrial setting. 

\subsection{Problem formulation}
\label{sec:problem_formulation}
\label{problem} 

To investigate this problem, the following research questions are asked:
\begin{itemize}
    \item To what extent do AI-generated software test cases achieve requirement-level test coverage compared to baseline or manually created test cases? 
    \item How efficiently can AI-generated test cases achieve requirement-level coverage in terms of the number of test cases required compared to baseline approaches?
\end{itemize}

This thesis investigates whether AI can be used to automatically generate software test cases from system requirements and other related system information. This system information can include interfaces, inputs and outputs, Controller Area Network (CAN) signals, and other relevant parameters. In many software projects, writing test cases is a manual task that takes time and often requires experience \cite{mustafa2021automated}. Because of this, it is important to study whether AI can support this work.

The main problem in this thesis is not only whether AI can generate test cases, but how useful those test cases are in practice. A good test case generation method should not only create many test cases. It should create test cases that cover the requirements well, while also avoiding more test cases than necessary.

For this reason, the thesis focuses on two main aspects. The first is requirement-level test coverage, which means how well the generated test cases cover the requirements compared to baseline or manually created test cases. The second is efficiency, which in this thesis means how many test cases are needed to achieve that coverage. In other words, the study looks at both how much is covered and how efficiently that coverage is reached.

The goal of the thesis is to evaluate whether AI-generated test cases can be a useful support in software testing. More specifically, the study aims to give a clearer understanding of the strengths and limitations of using AI for test case generation based on requirements and system-related information.

\subsection{Motivation}
This problem is relevant because software testing helps improve system quality and reliability. When requirements are written in natural language, creating test cases often requires manual interpretation by test engineers, which can make the process time-consuming and difficult to standardize. This may lead to inconsistencies, redundant test cases, and lower efficiency.

The problem is relevant not only for Volvo Construction Equipment, but also for companies working with embedded systems and industrial software development, where requirements are often complex and closely connected to testing. In such contexts, there is a practical need for more structured and scalable ways to connect requirements to test design. If test case generation can be automated or supported by AI, it may reduce effort, improve consistency, and support a more efficient testing process.

\subsection{Scope/Limitation}
This project focuses on investigating whether an already existing large language model can be used to generate system test cases from requirements. One limitation is that the project only works with the existing AI solution and does not involve building a new model from scratch.

The project is also limited to system test case generation. Other types of testing, such as unit testing, integration testing, and performance testing, are not included. Another limitation is that the study is carried out in one industrial context, Volvo Construction Equipment, which means that the results are mainly relevant to that setting and may not apply in exactly the same way in other companies or domains.

In addition, the project only uses the requirement material available in the project and does not include all possible types of requirements or documentation formats. It also does not compare all available AI tools or language models, but focuses on the existing model used in the project.

The agent is also limited by token usage, since large language models can only process a limited amount of input and output text at one prompt. This means that long requirements, system information, I/O descriptions, or other supporting documents may need to be shortened or split into smaller parts before they are processed by the AI agent. As a result, some contextual information may be reduced, which can affect the generated test \cite{openaiTokens}.

Another limitation is that the agent only produces system test cases in text format rather than executable test code. Therefore, the generated test cases can support the development of executable tests, but additional manual work is still required to implement and run them.

\section{Theory}
The purpose of this chapter is to present the theoretical background relevant to the project. It includes theory and previous research related to software testing, automated test case generation, large language models (LLMs), and the use of LLMs in software engineering and software testing. These areas are important for understanding the problem studied in this degree project.

\subsection{Software testing fundamentals}
Software testing is a fundamental part of developing software systems, and it is used to verify that the system behaves as expected and that its requirements are fulfilled. In software testing, there are primarily three levels of testing, including unit testing, integration testing, and system testing. Unit testing focuses on individual components of the system, integration testing focuses on multiple components working together, while system testing focuses on the system as a whole \cite{testing_study_2020}.

System testing is often performed as black-box testing, which means that only the system interfaces are tested and based on the requirements, it is examined whether the system fulfills its expected behavior. From the requirements, test cases are defined as a sequence of actions to be performed during testing, including the necessary execution steps and the expected results for each step \cite{testing_study_2020, luo2001softwaretesting}.

\subsection{System testing}
A related concept is end-to-end testing. End-to-end testing usually focuses on complete flows through the system, for example from user input to final output. This is similar to system testing in the sense that both look at the behavior of the full system. However, system testing is broader and focuses more generally on whether the whole system meets its specified requirements. For this reason, system testing is the more suitable concept in this project \cite{istqbE2E}.

System testing can also be challenging. Whittaker \cite{whittaker2002software} explains that software testing is difficult because software behavior can be complex and because testers must consider many possible situations, inputs, and interactions. In larger systems, this becomes even more demanding, since the complete system may include many connected parts, dependencies, and possible execution paths. This makes it difficult to test everything fully in practice. 

Another difficulty is that system testing often involves many possible inputs, outputs, states, and interactions. Luo \cite{luo2001softwaretesting} explains that testing involves selecting inputs, executing the software, and analysing the outputs. In larger systems, this selection becomes important because testers need to decide which scenarios are most relevant to test. This creates a risk that some requirements, edge cases, or interactions are not covered by the test cases.

System testing focuses on evaluating the complete system against its specified requirements \cite{istqbSystemTesting}. This makes system test cases important in this thesis, because the generated test cases are evaluated based on how well they cover the requirements. If relevant requirements, scenarios, or system behaviours are not included in the test cases, this may affect the measured requirement coverage. Therefore, the test cases need to be clear, connected to the requirements, and focused on relevant system behaviours.

\subsection{Test Case Design Techniques}
One common approach is requirement-based testing, where test cases are defined from system requirements. This ensures that system behavior is validated against its specification, although it often relies on manual interpretation \cite{luo2001softwaretesting}.

Scenario-based testing focuses on constructing test cases from realistic usage scenarios. These scenarios represent end-to-end interactions and are particularly relevant for system-level validation \cite{sommerville2016software}.

Techniques such as \textit{equivalence partitioning} and \textit{boundary value analysis} are used to systematically select input data. 
\textit{Equivalence partitioning} divides input data into groups that are expected to be processed similarly by the system. By selecting representative values from each group, the number of test cases can be reduced while still maintaining effective coverage.
\textit{Boundary value analysis} focuses on testing values at the edges of input ranges, where errors are more likely to occur. This helps to identify faults related to limits and constraints.
These techniques improve test efficiency while still addressing the areas where errors are more likely to occur \cite{sommerville2016software}.


\subsection{Model-based Testing}
Model-based testing (MBT) is a testing approach where test cases are generated from a model of the system instead of being created manually. The model describes the expected behavior of the system, and the generated test cases are based on that model. Dalal et al. \cite{dalal1999model} describe model-based testing as a way of generating test cases from requirements by using models of the system behavior. This makes the testing process more systematic and supports a higher degree of automation. In the same direction, Pretschner explains that model-based testing relies on models or specifications that encode the intended behavior of a system, and that runs of the model can be interpreted as test cases \cite{pretschner2005mbt}.

A central idea in MBT is therefore that the model represents the expected behaviour of the system, and that test cases are created based on this model. This makes the testing process more systematic and can support a higher degree of automation than fully manual test design \cite{dalal1999model,pretschner2005mbt}. El-Far and Whittaker also describe model-based software testing as an approach where models are used to guide test selection and test verification \cite{ibrahim2001model}.

\subsection{Software Requirements Specification (SRS)}
Software requirements describe what a software system is expected to do and what conditions it must fulfil. When such requirements are documented in a structured way, they can be used as a requirements specification. Bhatia et al. \cite{bhatia2024system} use requirements specification documents as input when studying system test case design with ChatGPT-4o, which shows that such documents can be used as a basis for creating system test cases.

Requirements are important in testing because they describe the expected behaviour that the system should be checked against. Mustafa et al. \cite{mustafa2021automated} discuss automated test case generation from requirements, where requirements are used as input for creating test cases. This is relevant in this thesis because the AI agent uses requirement material as input when generating system test cases.


\subsection{Evaluation Criteria for Generated Test Cases}
Evaluation of test cases is an important part of automated test case generation, since the quality of the generated output must be assessed before it can be considered useful in practice. In this context, generated test cases can be evaluated based on several criteria, such as correctness, completeness, verifiability, traceability, and unambiguous.

\subsubsection{Correctness}
An SRS is correct if its requirements match what the software is supposed to do. Since no tool can guarantee this automatically, the document needs to be checked against other specifications, project documents, and relevant standards. It can also be reviewed by customers or users to confirm that it reflects actual needs. Traceability helps by making these checks easier and reducing errors \cite{doe2011recommended}.

\subsubsection{Completeness}
An SRS is complete if it contains all important requirements for the software. This includes functional requirements, performance requirements, design constraints, quality-related requirements, and external interfaces. A complete SRS should also describe how the software responds to different types of input and situations, including invalid input. In addition, figures, tables, and diagrams should be clearly referenced, and all important terms and units should be explained \cite{doe2011recommended}.

\subsubsection{Verifiability}
A requirement is verifiable if there is a clear and practical way to check whether the software fulfills it. This means that the requirement must be specific enough to be tested or measured. In general, ambiguous requirements are not verifiable, because it is not possible to determine objectively whether they have been satisfied. Verifiability is important in software testing because requirements need to be written in a way that allows testers to determine whether the expected behavior has been achieved \cite{doe2011recommended}.

\subsubsection{Traceability}
Traceability means that a test case can be linked to the requirement or requirements it is intended to verify. In other words, it should be possible to see which requirement a test case comes from and what it is meant to test. This is important because traceability helps ensure that requirements are properly covered by the test process and makes it easier to identify missing or redundant test cases. In automated test case generation, traceability is particularly relevant, since it allows the generated test cases to be connected back to the original requirements and supports a more structured evaluation of the results \cite{doe2011recommended}.

\subsubsection{Unambiguous}
An SRS is unambiguous if each requirement can only be understood in one way. This means that the wording should be clear and consistent, so that different people do not interpret the requirement differently. If a term can have several meanings, it should be explained more clearly. This is important because software requirements are used by different groups, such as developers, testers, and users, who may not have the same background. If a requirement is ambiguous, it can create misunderstandings and make it harder to design, implement, and test the system correctly. In automated test case generation, this becomes even more important, since unclear requirements may lead to incorrect or unstable generated test cases \cite{doe2011recommended}.


\subsection{Large Language Models (LLMs)}
LLMs are artificial intelligence models trained on very large amounts of text. This allows them to recognize patterns in language and produce text that often seems natural and understandable. Recent research shows that LLMs have become important in many areas of software engineering. Zhang et al. \cite{zhang2026survey} show that LLMs are being studied across several software engineering phases, including requirements, development, testing, maintenance, and management.

One important reason for the rapid development of LLMs is the transformer architecture. Vaswani et al. \cite{vaswani2017attention} introduced the Transformer as a new neural network architecture based on attention mechanisms. Many modern LLMs are based on this architecture. Zhao et al. \cite{zhao2023survey} explain that pretrained language models were first developed by training Transformer models on large amounts of text. When these models were later scaled up with more data and computing power, they developed into large language models.

Because LLMs are designed to process and generate natural language, they can be used for many different tasks, such as text generation, summarization, translation, and question answering. They have also become increasingly common in technical domains. In software engineering, they are being explored for tasks such as code generation, documentation, repair, and testing \cite{zhang2026survey}.

In software testing, Wang et al. \cite{wang2024software} describe LLM-based testing as a growing research area. Their survey shows that LLMs are already being used for several testing-related tasks, such as test design, test generation, and other forms of testing support. This suggests that LLMs are not only useful for general language tasks, but also have potential in more specialized software engineering contexts.

At the same time, LLMs also have limitations. The output they generate is not always correct, complete, or consistent. Because of this, the results produced by LLMs often need to be reviewed carefully before they can be used in practice. This is also discussed in survey research on LLMs in software engineering and software testing \cite{zhang2026survey,wang2024software}.

\subsection{Automated Test Case Generation}

Automated test case generation has long been studied as a way to reduce the manual effort involved in software testing. Traditional approaches commonly generate test cases from requirements, UML models, activity diagrams, or other structured representations of system behavior \cite{mustafa2021automated}.

However, these approaches often depend on models or specifications that must be created and maintained manually. This can become difficult in complex systems, especially when documentation is incomplete or when the requirements are mainly expressed in natural language \cite{mustafa2021automated}.

More recent research has explored the use of large language models for test generation. For example, Bhatia et al. show that ChatGPT-4o can generate system test case designs from software requirements specifications, with a large share of the generated test cases judged as valid by developers \cite{bhatia2024system}.

At the same time, current LLM-based approaches still have important limitations. Dakhel et al. show that LLM-generated tests can contain syntactic or functional errors and may miss corner cases unless additional refinement and post-processing steps are applied \cite{dakhel2024effective}. Recent review work also shows that pre-processing, post-processing, and evaluation remain central challenges in LLM-based test case generation \cite{tasarsu2026slr}.

This suggests a gap between the flexibility offered by LLMs and the reliability required in practical test generation. In this thesis, that gap is addressed by exploring an AI-agent-based approach for generating and refining system-level test cases from requirements.

\subsection{AI-Agents}
AI agents are systems that are designed to carry out tasks more independently than a normal LLM. Instead of only giving one response, an AI agent is often built to work toward a goal through several steps. Research on LLM-based autonomous agents describes these systems as an extension of ordinary language models, where the model is given a more active role in solving tasks \cite{wang2024survey}.

A common way to describe AI agents is through their different parts. Wang et al. \cite{wang2024survey} explain that LLM-based agents can include functions such as memory, planning, and action. This means that an agent does not only generate text, but can also keep track of information, decide what to do next, and perform actions in a more structured way.

Another important difference is that AI agents are often designed to interact with external tools, resources, or environments. Liu et al. \cite{liu2024large} explain that LLM-based agents in software engineering extend ordinary LLMs by allowing them to use external tools and resources. This makes them useful in more complex tasks where one answer is not enough and where several steps may be needed to complete the task.

\subsection{System Interfaces}
The following sections briefly describe the Interfaces for system testing.

\subsubsection{CAN Signals}
Controller Area Network (CAN) signals are used to communicate information between different control units in the system. Each signal represents a specific value or state, such as sensor data, status information, or commands. In testing, CAN signals can be monitored to verify that the correct messages are sent, and they can also be simulated to test how the system reacts to specific input values or system states \cite{schneider_io}.

\subsubsection{Human-Machine Interface}
The Human-Machine Interface (HMI) is the part of the system that the user interacts with. It can include displays, buttons, indicators, or other visual feedback. The HMI is important because it shows how the system state is presented to the user and how the user can give input to the system \cite{nist_hmi}.

\subsubsection{Input and Output}
Input and output signals describe how the system receives information from its surroundings and how it responds. Inputs can come from sensors, buttons, or communication signals, while outputs can control actuators, lamps, displays, or other system components. These signals are relevant when defining and verifying test cases, since they connect the expected system behavior to measurable actions \cite{schneider_io}.

\subsection{Research Project}
Based on the problem formulation in Section \ref{sec:problem_formulation}, this thesis investigates the following research questions:

\begin{enumerate}
    \item To what extent do AI-generated software test cases achieve requirement-level test coverage compared to baseline or manually created test cases? 
    \item How efficiently can AI-generated test cases achieve requirement-level coverage in terms of the number of test cases required compared to baseline approaches?
\end{enumerate}

To answer these research questions, the study uses a combination of a literature review and a practical evaluation with both quantitative and qualitative elements.

The literature review provides a theoretical foundation for the study. It presents previous research related to software testing, requirements engineering, AI-based test case generation, and the evaluation of test case quality. It also helps define important concepts used in the thesis, such as requirement coverage. In addition, the literature review supports the research problem and helps motivate the design of the evaluation.

The first research question focuses on requirement-level test coverage. The purpose is to examine to what extent AI-generated test cases cover the relevant requirements. In this study, the AI-generated test cases are compared with manually created test cases developed by Volvo Construction Equipment, which serve as a baseline for comparison.

The second research question focuses on efficiency. In this thesis, efficiency refers to how well the generated test cases achieve requirement coverage in relation to the number of test cases produced. This means that the study examines not only whether the requirements are covered, but also whether this is done with a reasonable number of test cases and with as little unnecessary overlap as possible. The AI-generated test cases are therefore compared with Volvo’s manually created test cases in terms of the number of test cases needed to reach requirement coverage.

The quantitative part of the method is used to analyse measurable aspects, such as the number of covered requirements and the number of generated test cases, as well as differences between AI-generated and manually created test cases. The qualitative part is based on manual comparison between the AI-generated test cases and the manually created reference test cases. The comparison focuses on whether the generated test cases cover similar requirements and whether their steps align with the manually created test cases.

\subsection{Method}
The following subsection presents the different methods in more detail and explains how they relate to the research questions.

\subsubsection{Literature Review}
A literature review is used to examine previous research related to the topic of the study. It includes books, scientific articles, and other relevant sources in order to show what has already been studied in the research area. In this study, the literature review focused on software testing, AI-based test case generation, and the evaluation of test case quality. The reviewed literature was used to explain central concepts and to support the design of the study. 

\subsubsection{Quantitative Method}
A quantitative method is used when the study focuses on things that can be measured and expressed in numbers. Quantitative research is based on numerical data and is used to examine patterns, differences, or relationships in a structured way. It is often used when the researches wants to compare results or measure to what extend something occurs. Quantitative research is designed for purposes such as hypothesis testing, predictive modelling, and causal inference, which means that it focuses on measurable results rather than subjective interpretations \cite{lim2025quantitative}.

In this study, the quantitative part was based on comparing AI-generated test cases with manually created test cases from Volvo Construction Equipment. The comparison focused on the number of covered requirements and the number of generated test cases.


\subsubsection{Qualitative Method}
A qualitative method is used when the study focuses more on meaning, interpretation, and assessment than on numbers. It is often used when the researcher wants to understand how something is evaluated or understood in more depth. Instead of focusing mainly on measurable results, the qualitative method focuses more on judgement and interpretation \cite{usc_qualitative_method}.

In this study, the qualitative part was based on comparing the AI-generated test cases with the manually created reference test cases. The comparison focused on whether the test cases covered the same requirements and whether the test steps were similar, partly similar, or different. This helped show how closely the AI-generated test cases followed the manually created test cases.


\subsection{Reliability and Validity}
Reliability and validity are important in this study because the results depend on both the generated test cases and the way they are evaluated. Reliability refers whether the same results could be obtained if the study were repeated under similar conditions. One possible reliability issue in this thesis is that AI-generated test case may vary between runs, even when the same requirements are used as input. The test generation was tested several times during the development of the study. However, the final evaluation was based on one final AI-generated set of test cases. Because AI-generated test cases may vary between runs, the result should be understood as the outcome of that specific generation run. This can be seen as a reliability limitation. This can make it difficult to achieve fully consistent results. Reliability may also be affected by the the manual comparison, since the assessment of requirement coverage and efficiency includes human judgment. To  reduce this problem, the study uses the same input material, the same requirements, and the same general evaluation criteria when comparing AI-generated test cases with manually created test cases from Volvo Construction Equipment. 

Validity refers to whether the study actually measures what it intends to measure, and whether the conclusions are supported by the method and the collected data. In this thesis, validity is supported by the fact that the evaluation is directly connected to the research questions. Requirement-level coverage is examined by comparing the generated test cases and the manually created test cases against the same set of requirements. Efficiency is examined by comparing coverage in relation to the number of test cases and by considering redundancy between test cases. The inclusion of manually created test cases from Volvo Construction Equipment as a baseline also strengthens the validity of the study, since it provides a relevant practical comparison. At the same time, there are threats to validity. The manual comparison may be influenced by personal interpretation. Also, if the requirements are unclear or incomplete, it can be difficult to decide whether they are covered by the test cases. Another limitation is that the study is based on one specific industrial case, which means that the results may not be the same in other companies or domains.

\section{Implementation}
This chapter describes the implementation of the AI-based test case generation agent. It first gives an overview of the system architecture and then explains how input data, such as requirements and interface information, is handled. The chapter continues by describing the requirement parsing step, the LangChain pipeline, the prompt design, and how test cases and traceability information are generated. Finally, the chapter presents the output validation step used to check requirement coverage, as well as the configuration and model settings used in the implementation.

\subsection{System overview}
Figure~\ref{fig:system-architecture} presents an overview of the architecture of the implemented system. The blue box on the left represents the input data provided by the company. This input includes requirements, I/O descriptions, CAN signals, HMI behaviors, and the test strategy. Together, these inputs form the basis for the AI-based test case generation pipeline.

The purple box in the middle represents the LangChain prompting stage, which contains the three main generation steps of the system: requirement parsing, test case generation, and traceability generation. In the first step, the requirements are restructured into a more structured and test-oriented format, making them easier for the following steps to process. In the second step, the structured requirements are used together with the relevant system information to generate system-level test cases. In the third step, the generated test cases are connected back to the original requirements in order to produce traceability information.

The yellow box to the right of the prompting stage represents the large language model. At this stage, the prompts prepared in the previous step are sent to the LLM, which generates the corresponding outputs for each part of the pipeline.

The final step is shown in the blue output box on the right. This box represents the generated outputs of the system, including the parsed requirements, generated test cases, and traceability report. The test cases contain descriptions of the test steps and expected results, while the traceability output describes the connection between requirements and test cases. These outputs can later be used to analyze requirement coverage and evaluate the quality of the generated test cases.


\subsection{Input data handling}
The input data handling step is responsible for preparing the different types of input before they are passed to the agent. Instead of treating all input as one large text block, the data is separated into different categories, such as interface information, requirements and test strategy. This makes it clearer for the agent what each part of the input represents and how it should be used in the generation process.

This step is important because the LLM should not have to infer the purpose of the input by itself. By defining the input data more clearly, the system provides better context for the following steps and reduces the risk that the model uses the information in an incorrect or inconsistent way.

\subsection{Agent design}
The agent implemented in this project is a python class that separately calls the three different prompts and save the output. The first prompt preprocesses the requirements into a structured format, the second prompt generates system-level test cases, and the third prompt creates traceability information between the generated test cases and the original requirements.

Each prompt module used by the agent is responsible for a specific step in the generation pipeline. The agent is instantiated and executed from a Jupyter Notebook, where the required input data, including the test strategy, requirements, and interface descriptions, is loaded before the generation process begins. After each generation step, the output is validated using predefined Pydantic schemas. These schemas ensure that the generated responses follow the expected JSON structure and include the required field.

This structure allows the agent to handle the generation process step by step, where each prompt has a clearly defined role in the overall pipeline.

\subsection{LLM integration}
LangChain is used to manage the communication between the Python implementation and the selected language model. In this project, LangChain functions as an integration layer between the prompt modules and the LLM. It is used to send the prepared prompts to the model and return the generated responses to the agent.

The language model parameters are loaded from a shared configuration file within the prompt modules and are used when the model is initialized through LangChain. These parameters include settings such as the selected model and other generation parameters. 

Separating the model configuration from the main agent logic allows the same configuration to be reused across all the different prompt modules. It also makes the implementation easier to maintain, since changes to the LLM setup can be made in one place without modifying the prompt modules or the main agent workflow.

\subsection{Prompt Pipeline}
The following subsections are going to describe the three different prompts in more detail and what their objective are.

\subsubsection{Requirement preprocessing}
Before any test cases are generated, the agent preprocesses the requirements by transforming them into a structured and test-oriented format. This makes the requirements easier for the LLM to interpret and use as a basis for test case generation.

The output from the preprocessing step is represented as a list of JSON objects, where each object corresponds to one requirement. Each object includes the requirement ID, a short requirement description, and a list of functional test conditions. These conditions describe the behaviours or scenarios that should later be verified during test case generation.
\begin{lstlisting}[style=pythonstyle, caption={Preprocessed requirement format.}, label={lst:req-parsing}]
[
    {
      "id": "EXACT_REQUIREMENT_ID_FROM_INPUT",
      "description": "...",
      "conditions": [
      "condition 1"
      "condition 2"
      ],
    }
]
\end{lstlisting}

\newpage
\subsubsection{Test generation}
After the requirement preprocessing step, the agent generates the test cases. The test case prompt uses the preprocessed requirements, the system interface descriptions, and the test strategy to generate consistent system-level test cases.

The purpose of this prompt is to transform the structured requirement information into concrete test cases that describe how the system behaviour should be verified. The system interface descriptions are included to give the model information about available signals, inputs, outputs, and other system elements that may be needed when describing the test execution. The test strategy is used to guide the model toward generating test cases with a consistent structure and level of detail.

The output from this step is a list of generated test cases in JSON format. Each test case contains an identifier, a reference to one or more requirements, a short description, a sequence of test steps, and an expected result. This format makes the generated test cases easier to process, validate, and connect to the original requirements.

\begin{lstlisting}[style=pythonstyle, caption={Test case format.}, label={lst:test_generation}]
[
    {
      "id": "TC-1",
      "requirement_ids": ["EXACT_REQUIREMENT_ID_FROM_REQUIREMENT_DATA"],
      "description": "Verify that ...",
      "steps": [
        "Step 1",
        "Step 2",
        "Step 3"
      ],
      "expected_result": [
        "After Step 2, the system shall ...",
        "After Step 3, the system shall ..."
      ]
    }
]
\end{lstlisting}

\newpage
\subsubsection{Traceability report}
The final prompt is responsible for generating the traceability report. The inputs to this prompt are the preprocessed requirements and the test cases generated in the previous step. By comparing the requirement descriptions and functional test conditions with the generated test cases, the LLM identifies which requirements are covered by each test case. For each traceability entry, the model returns the test case identifier, all related requirement IDs, and a rationale explaining how the test case is covering the requirements.

This step is included to make the generated output easier to review and evaluate. Instead of only producing a list of test cases, the agent also provides information about how the test cases are connected to the requirement data. This supports traceability and helps determine whether the generated test cases cover the intended requirements.

\begin{lstlisting}[style=pythonstyle, caption={Traceability report format.}, label={lst:traceability_report}]
[
    {
      "testcase_id": "TC-1",
      "requirement_ids": ["EXACT_REQUIREMENT_ID_FROM_REQUIREMENT_DATA"],
      "reasoning": "This test case covers the requirement because..."
    }
]
\end{lstlisting}


\subsection{Test case strategy}

The test case strategy is defined in a separate file and is included as input to the test case generation prompt. Its purpose is to guide the LLM toward generating consistent and structured system-level test cases.

The strategy contains rules and constraints for how the test cases should be generated. These rules cover areas such as requirement traceability, use of available system interface descriptions, prevention of unsupported information, and the expected JSON output structure.

The test case strategy also includes guidance based on ISTQB testing terminology and principles. This includes instructions for how test cases should be structured, as well as references to test design techniques such as equivalence partitioning, boundary value analysis, decision table testing, and state transition testing. These instructions were included to guide the LLM toward generating structured and traceable test cases that are more consistent with established software testing practices \cite{istqbSystemTesting}.

The strategy is a plain-text YAML file consisting of different sections with instructions that guide the model during generation. By storing the strategy in a separate YAML file, it can be modified without changing the Python implementation or the main agent workflow.


\subsection{Output validation and Interface traceability}
After the test case have been generated, the output is validated to check whether all provided requirements are covered. This is done by comparing the requirement IDs from the input data with the requirements IDs linked to the generated test cases. 

This step does not evaluate whether each test case is correct or complete in terms of quality. Instead, it verifies that every requirement has at least one linked test case. This step is used to check whether all requirements are included in the generated test cases.

The program also generates an interface traceability report from the input interfaces and all generated test cases where the interfaces will be used. This report is generated by a simple search algorithm and is later used to validate each test case.



\subsection{Configuration and model settings}
The system uses \texttt{AzureChatOpenAI} to access the selected language model, GPT-5.4. The temperature parameter is set to \texttt{0} to reduce variation between runs, while \texttt{reasoning\_effort} is set to \texttt{None}, meaning that no specific reasoning effort level is explicitly requested \cite{langchain_azurechatopenai_docs}.

The model configuration is kept separate from the main pipeline logic. This makes the implementation easier to maintain, since model-related settings can be updated without changing the full system structure. Configuration values such as the model name, API endpoint, and API key are handled through configuration files or environment variables. This also helps avoid writing sensitive information directly in the source code.

\subsubsection{Experiment Purpose and Input Data}
The purpose of the experiment was to compare the AI-generated test cases with manually created test cases. The comparison focused on requirement-level coverage and the number of test cases needed to cover the same requirement set. In addition, a step-level comparison was performed to examine whether selected AI-generated test cases follows the same main test intention as the manually created reference test cases. 

The experiment used two test case sets. One set was generated by the developed AI pipeline, and the other set was manually created and used as the baseline. The interfaces and requirements used in the experiment were retrieved from a system activity, where 22 relevant requirements were identified. The comparison only included these 22 requirements, since they were the requirements that both test case sets had in common. As the manual test suite included additional requirements outside the scope of the activity, the comparison was limited to the test cases related to the 22 requirements identified from the activity.


Each test case was linked to one or more requirement IDs. These links were later used to calculate coverage, number of test cases, repeated links, and test-case matching. The linked requirement IDs were also used to identify which AI-generated and manually created test cases could be compared more closely in the step-level evaluation.

\subsubsection{Experimental Procedure}
The experiment was performed in four main stages. First, the selected input data was prepared and given to the AI pipeline. The pipeline then generated system-level test cases and traceability information for the generated test cases.

Second, the generated output was checked to make sure that each test case had a test case ID, linked requirement IDs, a description, test steps, and an expected result. This made the output possible to compare in a structured way.

Third, the AI-generated test cases and the manually created test cases were organized into comparison tables. These tables were then used as the basis for the result calculations presented in the next section.

The fourth test included a step-level comparison was performed for selected test cases where the AI-generated and manually created test cases were linked to the same requirements. This comparison was not performed only line by line, since the test cases did not always contain the same number of steps. Instead, the comparison focused on whether the same main setup, actions, and name elements were present. 


\subsubsection{Evaluation Metrics}
Five metrics were used in the comparison. Requirement coverage was used to measure how many requirements were covered by at least one test case. The number of test cases was used to compare how many test cases were needed in each test case set.

Requirement links were used to count how many requirement IDs were linked across all test cases. Repeated links were also counted to see how many requirement links appeared more than once.

Test-case matching was used to compare AI-generated test cases with manually created test cases. This matching was based on linked requirement IDs. A perfect match meant that the test cases covered the same requirement group, while a partial match meant that only some requirements overlapped.

A step-level color marking was also used as a supporting evaluation. The comparison focused on the detailed content of selected test cases, such as setup, action and named elements. Each relevant part was marked as green, yellow, or red. The green-marked steps represent steps that fully matched between the manually written test cases and the AI-generated test cases. The yellow-marked steps represent partial matches, where the steps described similar actions but used different variables, values, or levels of detail. The red-marked steps represent steps that did not have any corresponding match in the other test case.

\subsubsection{Requirement coverage results}
This section presents the requirement coverage for the AI-generated test suite and the manually created test suite. Requirement coverage was calculated by counting how many of the 22 shared requirements were linked to at least one test case. In this comparison, a requirement was counted as covered if it appeared in at least one test case.

The coverage was calculated as:

\section{Analysis}
\label{analysis}
This chapter analyses the results from the comparison between the AI-generated test cases and the manually created test cases. The analysis focuses on what the results mean in relation to requirement coverage, efficiency, requirement links, and test-case matching.

The purpose of the analysis is not to decide that one test case set is better in every aspect. Instead, the chapter discusses what can be concluded from the collected data and what cannot be concluded based on the selected metrics.

\subsection{Requirement Coverage}
The results show that both the AI-generated test cases and the manually created test cases covered all 22 shared requirements. This means that the AI-generated test cases achieved the same requirement-level coverage as the manual baseline in this experiment.

This result is relevant for the first research question, since it shows that the AI-generated test cases were able to cover the same shared requirement set as the manually created test cases. However, the result only shows coverage at requirement-ID level. It does not prove that the AI-generated test cases are equal to the manual test cases in all quality aspects.

For example, a requirement can be linked to a test case, but the test case may still be too general, unclear, or difficult to execute in practice. Therefore, the result should be interpreted as requirement-level coverage, not as a complete evaluation of test case quality.

\subsection{Test Case Efficiency}
The AI-generated test cases covered the 22 shared requirements using 7 test cases. The manually created test cases covered the same requirements using 9 test cases. This means that the AI-generated test case set was more compact in the experiment, because it reached the same requirements coverage with fewer test cases.

This result is connected to the second research question, which focuses on how efficiently AI-generated test cases can achieve requirement-level coverage. Based on the number of test cases, the AI-generated test cases were more efficient at requirement level.

However, fewer test cases are not always better. A smaller case set can be easier to review and maintain, but it can also make each test case broader. If one test case covers many requirements, it may become harder to understand, execute, or debug if the test fail. Therefore, the result shows better efficiency in terms of number of test cases, but not necessarily better practical test quality.

\subsection{Requirement Links and Repeated Links}
The AI-generated test cases had 22 total requirement link and 0 repeated links. The manually created test cases had 40 total requirement links and 18 repeated links. This means that each shared requirement appeared once in the AI-generated test case set, while several requirements appeared more than once in the manual test case set.

From a requirement-level view, the AI-generated test cases had less repetition. This supports the result that the AI-generated test case set was more compact. The AI pipeline created test cases where each requirement was covered without repeating the same requirement IDs across several test cases. 

However, repeated links in the manual test cases do not automatically mean that the manual test cases are worse or unnecessary. A requirement can be tested more than once in different situations. This can be useful if the requirement is important, complex, or needs to be checked in several scenarios. Therefore, the repeated links should be seen as an observation, not as proof that the manual test cases contain unnecessary duplication.

\subsection{Test-Case Matching}
The matching results show that 5 out of 7 AI-generated test cases had a perfect match with a manually created test case based on linked requirement IDs. The remaining 2 AI-generated test cases had partial matches. No AI-generated test case lacked a clear match.

This shows that most of the AI-generated test case were aligned with the manually created test case at requirement-link-level. In several cases, the AI-generated test cases covered the same requirement group as the manual test cases. This suggests that the AI pipeline was able to create test cases that were similar to the manual baseline in terms of requirement coverage.

The partial matches show that the AI pipeline sometimes grouped requirements differently from the manual test cases. This does not necessarily mean that the AI-generated test cases were wrong. It means that the AI and the manual test design did not always organize the requirements in the same way. To judge whether these differences are good or bad, the detailed test steps and expected results would need to be reviewed more closely.

\subsection{Test case step analysis}
The step-level evaluation was added because requirement-level coverage and requirement-link matching do not show the full content of the test cases. A test case can be linked to the correct requirement ID, but still differ from the manual reference test case in setup, actions, or named elements.

The color-based marking showed that the AI-generated test cases could be compared more clearly when the input names were aligned with the terminology used in the manual test cases. Green markings indicated that the AI-generated test case followed the same main test intention or performed the same function as the manual test case. Yellow markings indicated that the AI-generated test case was partly aligned, but missed some details or described them in a less specific way.

Red markings were interpreted carefully. They were not treated as direct proof that a test case was incorrect. Instead, they showed that a specific part could not be clearly matched between the AI-generated and manually created test cases. For the manual test cases, red markings often reflected additional detailed steps or verification points. For the AI-generated test cases, red markings often indicated that the generated step was more general, unclear, or not explicitly present in the manual reference test case. The results also show that the red color appears more frequently in the manually written test case steps. This suggests that the AI-generated steps are generally represented in the manual test cases, but that the manual test cases often include additional steps not generated by the AI agent. This can be interpreted as that the manually written test cases test functionality beyond what is explicitly specified in the requirements.

 This evaluation gives a more detailed view of the generated test cases than requirement coverage alone. However, the step-level evaluation should still be seen as a supporting analysis, not as a full expert review. It can show similarities and differences between the AI-generated and manually created test cases, but it cannot fully decide whether the test cases would work correctly in the real system.

Overall, the step-level evaluation showed that the AI-generated test cases often tested the same general behavior as the manually created test cases, even if the steps were not always written in the same way.

\subsection{Limitations of the Analysis}
This analysis has some limitations. The comparison was mainly based on linked requirement IDs. This means that the study checked whether each requirement was connected to at least one test case. To add more detail, a step-level evaluation was also performed on selected test cases.

For example, a test case can be linked to a requirement, but it may still be unclear, too general, or difficult to execute in practice. Because of this, the results should be seen as requirement-level results, not as a complete evaluation of test case quality.

The comparison was also limited to the shared requirements used in both test case sets. Therefore, the results should only be interpreted within this selected requirement scope.

\section{Discussion}
The problem formulation is presented in Chapter~\ref{sec:problem_formulation}. This section discusses the results in relation to the research questions and explains whether the questions have been answered. It also discusses how the findings relate to previous work in the field, as well as the strengths and limitations of the study. 

\subsection{Answering The Research Question}
The results show that the AI-generated test cases were able to cover the selected requirements at requirement level. This means that the covered requirements were linked to requirement IDs and that each selected requirement was covered at least once. To discuss the problem formulation we try to answer the research questions stated in section ~\ref{sec:problem_formulation}:

\begin{itemize}
    \item To what extent do AI-generated software test cases achieve requirement-level test coverage compared to baseline or manually created test cases? 
    \item How efficiently can AI-generated test cases achieve requirement-level coverage in terms of the number of test cases required compared to baseline approaches?
\end{itemize}

For the first research question, the results indicate that the AI-generated test cases can achieve strong requirement-level coverage when the input requirements and the prompt are structured in a clear way. Table~\ref{tab:requirement_coverage} shows that the agent generates test case with 100\% requirement coverage.

For the second research question, the results show how efficiently the AI-generated test cases achieved requirement coverage in terms of the number of test cases required. According to table~\ref{tab:testcase_efficiency} the AI-generated test suite used fewer test cases than the manual test suite, which can indicate higher efficiency. 

A possible reason why AI generated fewer test case is that the AI test cases were more compact and less detailed than the manually created test cases. The manual test cases often included more specific setup steps, detailed actions, and verification points. This can be because human tester has more knowledge and background information about the system, while AI mainly depends on the information given in the input. The step-level comparison shows that the steps in the AI-generated test cases generally match steps found in the manually written test cases, but not necessarily the other way around. This indicates that the manually written test cases often contain more detailed steps, and in some cases may include additional checks that go beyond what is explicitly stated in the requirement.
\subsection{Relation to previous work}
The findings of this study are in line with previous research on automated test case generation from requirements. Mustafa et al. \cite{mustafa2021automated} describe how requirements can be used as a basis for generating test cases automatically. This study supports that idea, since the AI-generated test cases were able to cover the selected requirements at requirement level.

The findings also relate to Wang et al. \cite{wang2024software}, who discuss the use of large language models in software testing. In this study, the LLM was able to generate test cases that were linked to requirement IDs, which shows that LLMs can support requirement-based test case generation.

\subsection{Strengths and Limitations}
This study evaluated AI-generated test cases by comparing them with manually created test cases at requirement level. The main focus was on requirement coverage and on how many test cases were needed to cover the selected requirements. This made it possible to evaluate whether the AI-generated test cases covered the same shared requirement set as the manual test cases.

A strength of this approach is that the comparison was based on requirement IDs. Since each test case was linked to one or more requirements, it was possible to check the coverage in a clear and structured way. This reduced the risk of only judging the test cases based on their wording, since two test cases can be written differently but still cover the same requirement.

Another strength is that the study included both AI-generated and manually created test cases. The manual test cases were used as a baseline, which made it possible to compare the AI-generated output with an existing test suite. This made the result more useful than only looking at the AI-generated test cases by themselves.

Traceability was also an important strength in this study. Since the generated test cases were linked to requirement IDs, the evaluation became more structured and easier to verify. This made it possible to check requirement coverage in a clear way, instead of only reading the test cases manually and trying to decide which requirements they covered.

Another strength is that the study did not only rely on requirement-level coverage. A step-level evaluation was also included to compare selected AI-generated and manually created test cases in more detail. This made it possible to examine whether the AI-generated test cases followed the same main test intention, actions, and expected results as the manual baseline.

However, a limitations is that the evaluation does not fully show whether each generated test case would work correctly in the real system. The study includes requirement-level coverage and a step-level evaluation, which gives a more detailed view of the test cases. However, the step-level evaluation is still only a supporting analysis. It can show similarities and differences between the AI-generated and manually created test cases, but it cannot fully confirm the quality or practical usefulness of each test case.

Another limitation is that the study was based on a selected requirement set. Therefore, the results should not be interpreted as proof that the method works equally well for all types of requirements or all systems. More requirements and more system functions would need to be tested to make the result more general.

The results can also be affected by the structure of the input and the prompt. Since the requirements were given with clear requirement IDs and the prompt instructed the model to cover all requirements, the result may depend on how well the input and prompt were prepared. If the requirements were less clear or less structured, the generated test cases might have been different.

\section{Conclusion}
This thesis has investigated whether an AI agent based on large language models can be used to automatically generate system-level test cases from requirements and interface descriptions. The aim was to explore whether such an approach could be used to produce structured test cases in a more automated way.

The implemented solution works like a pipeline where requirements are first preprocessed into a more structured format, then used together with interface information and a test strategy to generate system-level test cases. Finally, a traceability report is generated to connect the produced test cases back to the original requirements. The system was implemented using Python, and the use of the LangChain utilities to communicate with the LLM.

The results show that the AI agent is able to generate test cases that cover the provided requirements and maintain traceability between requirements and generated tests. The use of a separate test strategy has also helped guide the model toward a more consistent and structured output. In particular, the generated test cases were often more compact than the manually written test cases, since the AI agent grouped related requirements into fewer test scenarios when possible.

However, the results also show that automatic test case generation has limitations. The generated test cases depend heavily on the quality and completeness of the input requirements and interface descriptions. In some cases, the model may produce test steps that are less detailed than manual test cases, or exclude practical aspects that a human tester would normally include. Therefore, the generated test cases should not be seen as a complete replacement for manual test design, but rather as a supporting tool that can reduce repetitive work and provide an initial test case structure.

In conclusion, the thesis demonstrates that an LLM-based AI agent can be used to support system-level test case generation and traceability. The approach shows potential for improving efficiency in the test design process, especially in early stages where requirements need to be transformed into structured test scenarios. 

\subsection{Future work}
Future work could investigate how the underlying LLM setup can be optimized for system-level test case generation. This could include both the selection of the language model and the configuration of model parameters. Since different LLMs may differ in reasoning capability, output stability, instruction following, and ability to preserve traceability to requirements, several models could be used and compared with the same requirements, interface data. As part of the same investigation, different model configurations could also be evaluated. Parameters such as temperature and reasoning effort could be varied to study how they influence output consistency, requirement coverage, traceability quality, and the level of detail in the generated test cases.

Another aspect that was out of the scope of this thesis was whether it is possible to generate executable testing code directly from the same input. However, as this thesis has shown, the generated test cases still require manual interpretation before they can be executed in a real test environment.

Future work could therefore investigate how the generated system-level test cases can be transformed into executable test scripts. This would require a closer connection between the generated test steps and the available test environment, for example by mapping each step to concrete system inputs, interface signals or an expected outputs. In such an extension, the use of helper methods would become important, since they could be used to represent several lower-level test actions as a single reusable operation. For example, a high-level step in a generated test case could be mapped to a helper method that performs the required sequence of interface interactions in the test environment.
